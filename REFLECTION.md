# REFLECTION.md — Engineering Reflection

This document answers the five required reflective engineering questions regarding the investigation, architecture, and implementation of the **Urja Meter Operations API** service.

---

### 1. What assumptions did you make?

1. **Authentication Session Lifetime & Renewal**:
   - We observed that the upstream SvelteKit backend utilizes Better-Auth with the `__Secure-better-auth.session_token` cookie.
   - We assumed the session token may expire intermittently during prolonged execution; consequently, we implemented automatic re-authentication logic with controlled one-shot retries on `401` or redirect-to-login responses.
2. **Network Hierarchy Representation**:
   - In individual meter endpoints (`/portal/meters/search`), only the `dtCode` is directly returned. However, `/portal/export` exposes the full 7-tier geographic and electrical hierarchy (`zone` -> `circle` -> `division` -> `subdivision` -> `substation` -> `feeder` -> `dt`).
   - For `GET /api/meters/:id/network`, we assumed clients prefer the rich 7-tier hierarchy when available, while falling back gracefully to distribution transformer and coordinate metadata if the export payload is unreachable.
3. **Consumption Units & Timezone**:
   - The portal provides timestamps in Indian date format (`DD/MM/YYYY HH:mm`) without an explicit timezone offset. We assumed that electricity telemetry generated by Jaipur/Rajasthan discom meters corresponds to Indian Standard Time (IST, UTC+05:30), but converted the parsed values into standardized ISO 8601 UTC strings while preserving the raw timestamp to avoid data loss.
4. **Numeric String Conversion**:
   - Because coordinates and meter telemetry are returned as strings (e.g. `"latitude": "26.9389..."` and `"kwh": "48438.74"`), we assumed downstream consumers expect IEEE 754 floating-point numbers in standard JSON, and added parsing while safeguarding against `NaN` values.

---

### 2. Which part was most difficult, and how did you get unstuck?

- **The Challenge**: The most challenging aspect was discovering and reverse-engineering the HMAC signing requirements for the `/portal/export` endpoint. Standard GET requests to `/portal/export` failed with HTTP 401/403 missing header errors.
- **How We Got Unstuck**:
  - By inspecting the SvelteKit frontend bundle and related API paths, we located `/portal/keys`, which returned an active `signingSecret` and expiration interval.
  - Analyzing the client-side signing logic revealed the canonical message string format: `METHOD\nPATH\nQUERY_STRING\nTIMESTAMP`, which was then hashed using HMAC-SHA256 and sent via `x-timestamp` and `x-signature` headers.
  - Once implemented in `src/utils/hmac.js`, requests to `/portal/export` succeeded consistently, revealing complete meter coordinates and electrical hierarchy for all 403 network meters.

---

### 3. If you had another day, what would you improve?

1. **In-Memory / Redis Caching for Static Metadata**:
   - Transformer records (`/portal/dts`) and network hierarchy records change infrequently compared to interval consumption readings. Adding short-lived caching with TTL (e.g. 5–15 minutes) would reduce load on the upstream legacy portal.
2. **Parallel Bulk Extraction & Ingestion Pipeline**:
   - Provide an asynchronous job or stream endpoint to ingest and index all 403 meters and their historical consumption into an analytical store (such as SQLite or DuckDB for fast local queries).
3. **Comprehensive Rate-Limiting & Concurrency Throttling**:
   - Add a leaky-bucket or p-limit concurrency queue to ensure requests sent by multi-user clients do not overwhelm the single-operator session on the legacy server.
4. **Prometheus Telemetry Metrics**:
   - Expose `/metrics` with standard RED metrics (Rate, Errors, Duration) and upstream latency histograms.

---

### 4. What mistake did you make while solving this?

- **Initial Port Collision (`EADDRINUSE`)**:
  - During initial server boot, the process failed because port `3000` was already occupied by another local service on the host machine.
  - Rather than hardcoding alternative ports or killing unrelated processes blindly, we verified and updated `.env` to support configurable ports (`PORT=3001` or `3000`), ensuring the service is environment-agnostic.
- **Timestamp Parsing Bug**:
  - An early prototype parsed `23/06/2026 23:30` using standard `new Date('23/06/2026')`, which in V8 JavaScript fails with `Invalid Date` because it expects US format `MM/DD/YYYY`.
  - We promptly created a dedicated parser `parseIndianDateToIso` in `src/utils/normalizer.js` with explicit day/month/year splitting and test coverage.

---

### 5. If reviewing your own submission, what would you criticize?

1. **Composite Meter Endpoint Fan-Out**:
   - `GET /api/meters/:id` performs a `Promise.allSettled` query across search, geolocation, and energy telemetry to build a complete profile. While convenient for clients, this makes 3 upstream HTTP calls per meter detail request.
2. **Single Portal Session Shared Across Requests**:
   - The API uses a shared `PortalClient` instance with one operator credential session. If multiple concurrent requests trigger a re-login at the exact same millisecond, simultaneous login requests could race. Adding a mutex/lock around the login flow would make high-concurrency re-authentication even more robust.
3. **Mock vs Real Distinction**:
   - While we established separate automated unit test suites (`tests/*.test.js`) and live integration tests (`tests/integration.test.js`), maintaining mocks manually when upstream portal schemas evolve requires periodic re-validation.
